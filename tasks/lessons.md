# lessons.md — 本项目的问题模式与我的规则

> 📍 交接导航：本文件是**工程纪律清单**（每条附真实事故佐证）。
> 当前状态、未闭合风险与红线见 **[docs/HANDOFF.md](../docs/HANDOFF.md)**；通用约定见 **[AGENTS.md](../AGENTS.md)**。

## L1. 验收清单不完整：只查了「好不好看」，没查「全不全」

**发生**：2026-10-09。字号保真那一轮，我做了 15 页逐页视觉审板，但审板清单只有
「字号 / 碰撞 / 垂直基线 / 选项分隔 / 分式 / 裁切」六项 —— **没有「内容是否齐全」**。
结果第 9 页第 10 题题干被截断（丢了 3 行）这种一眼可见的问题被漏过，
被用户当场指出：「第9页哪止这一个问题啊？第10题，题干都没了」。

**根因**：我把审板清单建立在「本轮改了什么」之上（改字号 → 查字号），
而不是建立在「**项目红线**」之上。本项目第一条红线是「不静默失败 / 不丢内容」，
审板清单里却没有它。

**规则**：
- 审板清单的第一项永远是「**内容齐全性**」：逐页对照原卷，逐题核对题干、选项、插图是否齐全。
- 清单来源是**红线**，不是**本轮改动**。改动只是要额外加查的项，不能替代红线项。
- 判据粒度决定漏检粒度（本项目 §17 已有此教训）——**这次是同一类错误换了个面**：
  判据的**覆盖面**（查了哪些维度）和判据的**粒度**（阈值多细）一样会决定漏检。

## L2. 「搬迁/丢弃」类启发式规则：形状判据用 OR 放宽 → 误判即静默丢内容

**发生**：`src/normalize.ts` 的 `isCrossPageLeakShape`（2026-10-07 为修 p0 q7 题干截断而写）
用 `noOverlap = x不相交 或 y不相交` 作为形状判据。双栏排版下，「左栏底部的段」与
「右栏顶部的行」天然 **x 不相交**，于是被误判成「跨页泄漏」，那 3 行被迁到下一页
（第 10 页顶部，压在它自己的标题上）。**两个可见缺陷**：第 9 页题干截断 + 第 10 页幽灵行。

**根因**：形状判据里的 OR 让「跨栏」被当成了「跨页」。而规则的动作是**搬迁**，
误判的后果不是「不动」而是「**静默搬走**」——直接踩红线。

**规则**：
- 任何「搬迁 / 丢弃 / 改写」类启发式规则，判据必须**最严**（AND），宁可漏判也不能误判：
  漏判只是「没修好」，误判是「把好的弄坏了还看不出来」。
- 这类规则必须带**同页守卫**：同一页内的元素不得互相搬迁。
- 这类规则必须产出**可核对记录**（搬了哪些、从哪到哪），并在展示层可见。
- 规则的回归验收必须包含「**它当初要修的那个案例仍然成立**」——
  修新缺陷时不能把老缺陷放回来。

## L3. 别把「探针命中」当结论：跨块拼接会造假阳性

**发生**：本轮诊断时我先用「把整页文本拼接起来再 includes 探针」的方式判断内容是否真丢，
得到「哑块（内容在别处）」的结论；但拼接时我把块间分隔符也归一化掉了，
**跨块边界可能拼出并不存在的字符串**。改成**逐块独立匹配**后结论才可靠。

**规则**：判断「某段文字是否还在」时，必须**逐块独立匹配**，不得先拼接再匹配。
拼接会制造假阳性（把"丢"判成"没丢"），这是最危险的方向——它会让缺陷隐身。

## L4. 多会话并行：worktree 的 `data/` 是软链 ⇒ 产物目录被共享，后跑者覆盖先跑者

**发生**：2026-10-30。两个 Agent 会话并行执行同一条计划：会话 A 在功能 worktree
（`feature/oxr`）重导产物并跑 `bank:all`（显式绑定，420 条）；会话 B 在主仓库 `main`
跑 `npm run check` —— 它的 `bank:all` 用 main 的**旧代码**（无显式绑定）把共享的
`data/out/bank/` 覆盖成 476 条旧口径。功能 worktree 里的 `data`、`books` 是指向主仓库的
**绝对路径软链**（2026-10-27 为让新 worktree 能看到运行时产物而建）⇒ git 隔离了被跟踪
文件，**产物层根本不存在隔离**。此外，进入功能 worktree 收口未提交改动时，还实测遇到
另一会话**正在写入**（文件 mtime 距当时仅 3 分钟，且此后又出现新的未提交改动与提交）。

**根因**：git 的 worktree 隔离只覆盖被跟踪文件；`data/` 被软链后是**一个物理目录**，
两个会话都往里写，互相不知情，谁后跑谁覆盖 —— 且旧代码覆盖新产物的方向最危险
（看起来"门全绿"，实际口径倒退）。

**规则**：
- 在任何会话动手前先查三样：`git status`（有没有别人的未提交改动）、共享产物目录的
  **最近 mtime**（有新鲜写入 ⇒ 可能存在并行会话）、**进程列表**（有没有正在跑的
  batch / daily / export / view-server）。
- 「收口未提交 WIP」必须在 WIP 所在的 worktree **原地**做，不把改动搬回自己的工作区。
- 多个会话要执行同一条计划前先分工（或一方明确撤出）；发现产物被覆盖，先按正确口径
  重跑恢复再继续，并把事故记入台账。
- 质量门里**会写产物**的步骤（`bank:all`、重导、`daily`）是冲突热点；只读审计
  （`audit:ab`、`audit:render`、审计脚本）可以放心跑。
