# 反馈处理看板（B-73）· 设计与实施

> 2026-11-24 用户需求。用户原话：「我需要更好地掌控这个项目我提的问题的进展」+ 四条具体需求（见 BACKLOG B-73）。
> 用户明确「接下来由你完成长程任务，决策由你自己决策，我不在电脑边」。
> 本文件是设计 spec，按 §119 框架由 Agent 自决技术路径，需求口径已足够清晰不再追问。

## 一、目标与验收

**要解决的真问题**：反馈提交后，用户看不到「谁在处理、处理到哪、能不能插话」。现在的状态只有 `feedbacks.json` 里的 `status=open|working|fixed` 三档静态字，且中台侧（agent-autoloop）的进度完全不可见。

**验收标准（可量化）**：
1. 打开一个网页 URL，能看到**所有我提交的反馈**，每条显示：当前状态、**正在处理的 Agent 名**、**会话 ID**、最近一次活动时间。
2. 每条反馈有「**进入会话**」按钮，点了能**复制一行命令**（或一键进终端），执行后直接连上该会话。
3. 有待回答的对话（中台卡片 kind=ask 且 state=open）时，看板上**就地显示问题与选项**，点选项即完成回答（不等命令行）。
4. 状态自动刷新（无需手动刷页）。

## 二、数据源：只用中台 HTTP 接口，不自建状态

中台（agent-autoloop，本机 3350）原生无界面，但接口完整（协议 `app/docs/protocol.md`）：

| 用途 | 接口 | 密钥 |
|---|---|---|
| 全量状态 | `GET /v1/state` | owner |
| 翻更早轮次 | `GET /v1/state?before=<seq>` / `GET /v1/runs?rule=<名>` | owner |
| 事件→轮次关联 | `/v1/state` 的 `runs[].events[]`（含 id/type/subject/receivedAt） | owner |
| 回答卡片 | `POST /v1/cards/<id>/answer {choice\|text}` | owner |
| 结案卡片 | `POST /v1/cards/<id>/resolve {reason}` | owner |
| 实时推送 | `GET /v1/stream?after=<seq>`（SSE） | owner |

**密钥来源**：`~/.agent-autoloop/config.json` 的 `owner`。view-server 已在 `scripts/view-server.ts` 用 `AGENT_AUTOLOOP_*` env 读 source key；owner key 需要同样方式注入（`.local/view-server-env.sh` 增补 `AGENT_AUTOLOOP_OWNER_KEY`，动态读 config，不硬编码）。

**关键映射（反馈 ↔ 中台对象）**：
- 反馈条目 = `data/out/feedback/feedbacks.json` 的 items（id、status、reply、comment、shot）。
- 中台事件 = `feedback.created`，其 `subject` **就是反馈 id**（view-server `notifyAutoloop` 发时 subject=ev.id）。
- 轮次 run = 事件所在 run；`run.session` = 会话 ID；`run.agent.name` = 哪个 Agent。
- 待回答 = 卡片 `kind=ask && state=open`，卡片的 `lane`/`about` 关联事项（同一规则同一 subject 为一个事项）。

⇒ 一条反馈的完整画像 = `feedbacks.json 条目` + `events(subject=id) → runs[] → {agent, session, state, summary}` + `open cards`。

## 三、必须先补的硬缺口：会话 ID 拿不到

**实测**：`/v1/state` 的 `runs[].session` 恒为 `null`。
**根因**：Hermes 走 `use:"command"`，而 command 插件（`app/plugins/command/agent.ts`）的 `read()` 只返回 `{text: stdout}`，从不解析会话 id；worker 的 `conclude()` 从 `seen.session` 取，取不到就没有。

**修法（不改中台源码，加用户级插件）**：新建 `~/.agent-autoloop/plugins/hermes/agent.ts`，实现 `Adapter`：
- `command: (turn) => [hermesBin, "chat","-Q","-q", turn.prompt, "--provider","magpie","-m","longcat/LongCat-2.5"]`
- `read(stdout, code, stderr)`：扫 stdout 行，抓 `session_id:\s*(\S+)` → `seen.session`；最后一段非空文本作 `text`；`started:true`（进程起来就算）；`finished` 由退出码推断。
- `link: (session) => ...`（可选，给客户端用）。

rules.json 的 `agents.feedback.use` 从 `"command"` 改为 `"hermes"`，`command` 字段移除（插件自带命令）。**插件目录 `~/.agent-autoloop/plugins/hermes/` 需 gitignore 意识**：它在 `~/.agent-autoloop` 下（本就不在项目仓库），符合「密钥/本地配置不入项目仓库」红线。

**验证**：改后跑一轮，`GET /v1/state` 的 `runs[].session` 应出现 `local-<hex>`；`agent-autoloop why <run>` 能看到会话。

**风险**：插件加载失败会让所有 Hermes 轮次失败。先备份 rules.json，改后 `agent-autoloop check` 校验，再实跑一轮确认。

## 四、页面形态

**入口**：成品页顶栏新增「看板」按钮（与「知识点」「挑题」并列）→ 打开 `/board/`（独立轻页，复用 viewer.css 变量；或 final 页内弹层——倾向前者，保持 final 页纯粹）。

**布局（参考成熟看板）**：
- 顶部：统计条（待处理 N / 进行中 N / 已完成 N / 等你回答 N）。
- 主体：**按状态分列**（4 列）：`待处理`（open 且无活跃 run）、`处理中`（有 claimed/run 未结束）、`等你回答`（有 open ask 卡片）、`已了结`（fixed/closed）。
- 每张卡：反馈标题（comment 首行）、册名/页码、提交时间、**Agent 徽标**（哪个 Agent）、**状态徽标**、**会话 ID**（mono 字体 + 复制钮）、最近活动（run.summary 末行 / 卡片 title）。
- 「进入会话」：点击 → 弹层显示一行命令并复制：
  - Hermes：`~/.local/bin/hermes chat -Q --resume <session_id>`（`-r/--resume` 支持 SESSION_ID，见 `hermes chat --help`）
  - Claude：`claude -r <session_id>`
  - 通用：也提供 `agent-autoloop why <run> --json` 作为兜底。
- 「等你回答」卡：列出 options 按钮 + 自由文本框，提交即 `POST /v1/cards/<id>/answer`。

**实时性**：前端每 15s 轮询 `/api/board/state`（server 端聚合中台 state + feedbacks.json）；可选接 SSE（MVP 先用轮询，简单可靠）。

## 五、实施步骤（MVP 优先）

1. **补会话能力**：写 `~/.agent-autoloop/plugins/hermes/agent.ts` + 改 rules.json → 实跑一轮验证 `runs[].session` 非 null。
2. **后端聚合接口**：`scripts/board-state.ts`（纯函数，读 state+feedbacks 拼画像）+ view-server 路由 `/api/board/state`。TDD。
3. **前端页面**：`board/index.html` + `board/board.js`（`// @ts-check` + JSDoc 规则，DOM 文件不加 @ts-check——见 AGENTS.md 红线）。TDD 逻辑部分。
4. **接线**：final 页加「看板」入口；启动日志报告。
5. **验收**：全链路——提交反馈 → 中台派 Hermes → 看板显示 Agent/会话/状态 → 点「进入会话」得命令 → 制造一张 ask 卡片 → 看板就地回答 → 状态流转。

## 六、不做（YAGNI）

- 不做拖拽排序（状态由中台事实决定，不应人工改）。
- 不做多项目/多租户（中台就一个 rules.json）。
- 不搬「Harness 客户端」本体（中台无界面，Harness 若指 ZCode 客户端则它是桌面应用，无法搬到网页；我们只做数据打通）。
- 不改中台内核（插件/接口够了）。
- 一期不做 SSE（轮询够用；留接口以后换）。

## 七、风险与回滚

| 风险 | 缓解 |
|---|---|
| Hermes 插件加载失败导致派活全挂 | 改前备份 rules.json；`check` 校验；失败即回滚为 `use:"command"`（会话 ID 缺失但功能可用） |
| owner key 泄漏 | 只经 `.local/*.sh`（gitignore）注入，不写进仓库、不打印 |
| 看板与服务争端口 | 挂在既有 4173 view-server 下，不新开端口 |
| 回答卡片误操作 | 前端二次确认；接口对已结案卡片返回 changed:false 无副作用（已实测） |
