## 0. 背景与问题（一段话说清）

MinerU 作主解析源的结构价值（块/行坐标系）已被全引擎依赖，但它的**整行漏读**是量化的已知缺陷
（B-26：138 条修正中 100 条整行漏读 + 21 条字认错；本轮 14 个 A/B 洞 = 漏读行真值集）。
历史教训 N-07 曾以「行数 63→14 净退化」否决换源，但 **§111 已改判**：63→14 是 vlm 识别器的
行合并约定（文字覆盖率 92~99%），病根是**下游对行粒度的强依赖**——换源可行性必须按
「粒度归一化 + 下游去行粒度依赖」的新口径重评，本文档即该重评的立项申请。

## 2. 方案 A：OXR 换源生产化

**目标**：主解析源 MinerU → OXR；漏行解决率全册 ≥99%、新造漏行率 ≤1%；下游（切题/洞检测/补字/展示）
完成一次**去行粒度依赖**重构——判据按 OXR 粒度重标定，不硬套 MinerU 约定（§111 教训的正面落实）。

**工作分解**：
- A1 全册双向验证（187 页，免费档 ~10 批分片调用；复用 compare.py 出全册漏行/新造漏行分布）
- A2 粒度映射层：OXR 块（bbox/content/type）→ 引擎 block 约定（行切分、阅读顺序、题号脚印逐项重标定）
- A3 双轨并行期：MinerU 与 OXR 同跑双产物，对比 viewer 逐页人审（抽样 ≥20 页）
- A4 切换 + 回滚预案（stages 生成器双源开关；旧链路保留一个版本周期）

**风险与缓解**：
- 免费档无 SLA / 限流 ⇒ 分片重试已内建（oxr-client TIMEOUT 420s）；正式版 key 为后备（OXR_BASE_URL/OXR_API_KEY）
- 公式 LaTeX 口径：B-31 记录「OXR 3 行不包 LaTeX」⇒ 公式洞/公式行需单独口径（结合 jev 判决）
- 网格页（p185/p186）等未知页型在 OXR 下的表现未测 ⇒ A1 全册验证覆盖
- OXR 块合并怪癖（oxr-convert 含 dedupe 逻辑）⇒ A2 映射层吸收

**成本**：免费档为主；工时估算 A1 ≈0.5 天、A2 ≈2-3 天、A3 ≈1-2 天、A4 ≈0.5 天。

## 3. 方案 B：云端 VL 1.6 换源生产化

**目标**：同 A，源 = 云端 VL 1.6（jobs API）。识别质量上限更高（B-31 公式 0/23 全场并列最低）。

**工作分解**：
- B1 全册双向验证（187 页 jobs ≈ 40-50 分钟 + 配额费用）
- B2 **公式行恢复解析器（B 独有前置）**：VL 把公式行并成 content 为空的大块（本轮 23/25 未覆盖的根因），
  文字在 markdown/lines 层——需写「lines 层取文」解析器并验证恢复率 ≥95%
- B3 粒度映射层：VL 块粒度更粗（4 页 18-22 块 vs OXR 22-49 块），行级重建依赖 lines 层
- B4 双轨并行 + 切换（同 A3/A4）

**风险与缓解**：
- **配额/费用**：整本作业 + 每次重跑计费（L12 教训：范围纪律必须显式 --pages / 作业清单）
- 行合并形态的恢复残余风险：lines 层若仍有空 content 块 ⇒ 公式行成新洞（B2 验收门槛卡住）
- 厂商服务依赖；本地 VL 可行但 58s/页不作产线（已实测）

**成本**：全册作业 1 次 ≈ 40-50 分钟 + tokens；工时估算 B1 ≈0.5 天、B2 ≈2 天、B3 ≈2 天、B4 ≈0.5 天。

## 4. 两案对照与推荐

| 维度 | 方案 A（OXR） | 方案 B（云端 VL） |
|---|---|---|
| 漏行根除（4 页实证） | 100%，零附带 | 100%，真漏 0.7%（可修复项另计） |
| 独有前置工程 | 粒度映射层 | + 公式行 lines 层恢复解析器 |
| 成本结构 | 免费档为主 | 每次全册作业计费 |
| 识别质量上限 | 高（公式 0/22，但 3 行不包 LaTeX） | 更高（公式 0/23，LaTeX 内嵌） |
| 服务依赖 | 免费档无 SLA | 厂商作业队列 |

**推荐**：**A 先行**（零费用 + 双向审计满分 + 少一个前置解析器），**B 作并列验证与公式兜底**
（A 的公式口径缺口恰好由 B/jev 补）。两案共享 A1/B1 的全册验证基础设施。
