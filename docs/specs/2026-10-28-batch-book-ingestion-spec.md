# 批量扫书 · 高准确率录入规格（草案 v0.1）

- 状态：**草案 v0.2；2026-10-28 用户 ok = 按建议默认执行**；Phase 0 进行中（B02/B03/B04 已落地，F1 融合原型已评估，B01/B05 待续；真实 PDF 批量/100 本/日未验）
- 日期：2026-10-28
- 范围：把现有单本导入链路（`npm run daily`）升级为「每天批量导入大量书本 + 准确率可量化」的生产闭环
- 关联：`docs/HANDOFF.md` §1/§2/§6、`docs/DECISIONS.md`、`docs/dev/bgx/reports/20261028T174255+0800-REPORT-项目开发治理体检.md`
- 一句话：**先让准确率可测，再让吞吐可跑**；没有金标准的「准确率很高」不算指标。

## 1. 问题陈述

### 1.1 现在能做什么（实测基线，2026-10-28）

| 现状 | 数字 | 出处/说明 |
|---|---|---|
| 已处理文档 | **9 卷**（7 题册 + 1 个 23 页答案册 + 1 个 187 页合订本） | `data/out/*/stages.json` |
| 总页数 / 题数 / 组数 | **313 页 / 1,125 题 / 162 组** | 9 卷汇总 |
| 题库配对 | **420 条**（6 本题册；光学卷因无章标题跳过） | `npm run bank:all` |
| 待人工校对 | **178 题 / 1,125 = 15.8%**；单卷 1.2%–42.1%；**≤1% 的卷 0/9，≤5% 的卷 6/9** | `meta.json` 的 `needs_review` |
| 人工修正 | **185 条**：6 条 `disabled`，**57 条已应用但未逐条核对**（30.8%） | `corrections/*.json` |
| 审计覆盖 | 渲染 **8/8**（不含合订本，合订本基线未标定）；题号 **2/9**；题库 6 本题册 | `audit:render:all` / `audit-numbering` / `bank:all` |
| 输出体积 | **723 MB / 313 页**（≈2.3 MB/页，含页图/原卷/图片） | `du -sh data/out` |
| 批量能力 | **没有批量命令/队列/断点/台账/日报**；`daily` 一次一本；`real-pipeline` 能遍历目录但不跑 OCR/体检 | `scripts/daily.ts` / `real-pipeline.ts` |
| 吞吐 | 单本 15 页约 **30 秒**（历史记录）；187 页合订本、100 本/日、p95、成本均未测 | `docs/HANDOFF.md` §2 |
| 准确率 | **无法测**：没有金标准集，没有题目/选项/答案的召回率/精确率 | 本 spec 要补的第一件事 |

### 1.2 为什么值得解决

- **准确率不可证**：现在的 `needs_review` 是「引擎自己觉得可能有问题」的代理指标，不是「相对原卷对错」的准确率。15.8% 的待校对率既可能是保守，也可能是真错；没有金标准，任何「99%」都是口号。
- **吞吐不可跑**：每天大量扫书需要「投递 → 排队 → 断点续跑 → 失败隔离 → 日报」；现在只有一条单本命令，人工串行是瓶颈。
- **人工不可持续**：100 本/日、每本约 80 题 ≈ 8,000 题/日；按当前 15.8% 待校对 ≈ 1,264 题/日，人工看不完，也没排序/证据/复核预算。
- **修正层有隐藏风险**：57 条已应用但未核对的修正会直接进题库；p13 已经发生过「填错 insert 多一道重复题」。高准确率目标必须把修正也纳入度量与复核。

### 1.3 目标（方向，不是数字）

建立一个**每天可重复**的批量闭环：

```
inbox/（PDF）
  → 批量队列（哈希去重 / 断点 / 重试 / 失败隔离）
  → 单本流水线（解析 → OCR → 切题 → 校验 → 快照/体检）
  → 单本报告（题数/页数/待校对/逐项指标）
  → 只复核异常（复核队列 + 修正核验）
  → 金标准打分 / 日报 / 告警
```

**验收的最终形态**：每天投一批书，第二天早上看一张日报；95% 以上的书不需要人工逐题看，
需要看的题只占 ≤1%，且每一道都带原因与证据；所有准确率数字都能在 30 本金标准集上复现。

## 2. 方案概述（复用现有引擎，新增编排与度量）

### 2.1 不重写引擎

现有链路已经是可用的单本生产级骨架：
`normalize → layout → patterns/rule-engine → validation → export-stages → OCR/corrections → bank → display`。
本 spec **不改切题算法的主体**，只加三层：

| 层 | 新增 | 复用 |
|---|---|---|
| 度量 | 金标准集 + 单本评分器 `npm run score` + `npm run check:accuracy` | `questions.json` / `stages.json` / `meta.json`；独立金标准 |
| 编排 | `npm run batch -- <inbox>`：哈希、去重、队列、断点、重试、并发、台账、日报 | 每本仍调用现有 `daily` / `stages:export` / OCR 脚本 |
| 治理 | 复核队列 + 修正核验 + 逐卷审计 + 成本/存储 | `needs_review` / `ReviewNote` / `corrections/` / 现有审计 |

### 2.2 深模块接缝（测试打在哪）

| 接缝 | 稳定接口 | 说明 |
|---|---|---|
| 批量 | `npm run batch -- <inbox>` → `data/batch/ledger.jsonl` + 每本 `meta.json` | 单本失败不阻塞整批；同哈希不重复；断点续跑 |
| 评分 | `npm run score -- <docId>`；`npm run check:accuracy` | 输入：金标准标签 + `questions.json`；输出：召回/精确/选项/答案/图片/公式/复核率 |
| 复核 | 现有 `needs_review` + `ReviewNote` + `meta.health` | 不新增第二套状态；把原因/证据排序成队列 |
| 修正 | 现有 `corrections/`（含 `disabled`） | 57 条未核对必须先核验；不自动删 |
| 审计 | `audit:render:all`（8 卷）/ `audit-numbering` | 逐卷基线；不把渲染审计当语义准确率 |

### 2.3 不在本 spec 里做的事

- 不训练/微调新模型；不换 MinerU/OXR/OCR 供应商（先测清成本与失败率）。
- 不重做 viewer/final/stages 的 UI；批量报告先用 CLI/JSON/Markdown。
- 不做手写体、拍照透视校正、多栏之外的特殊版式；这些单独立项。
- 不自动删除/改写修正条目；不为追求数字放宽门禁。

## 3. 用户故事（编号，可独立验收）

- **U1 投递**：我把 20/100 本 PDF 放进 `inbox/`，运行一次命令，系统按顺序/并发处理，不需要逐本敲命令。
- **U2 断点**：批处理中途被杀掉/断网，我重跑同一条命令；已完成的书不重复跑、不重复写，未完成的书继续。
- **U3 去重**：同一本书重复投递（同文件哈希）不会生成第二份文档，也不会覆盖已人工复核的标签/修正。
- **U4 失败隔离**：某一本网络失败/解析失败，其他书继续；失败书有明确原因与重试状态，不阻塞整批。
- **U5 单本报告**：每本书有一份报告：页数、题数、组数、待校对、缺失/重复题号、图片/答案配对、耗时、成本、状态。
- **U6 日报**：每天一张日报：处理了多少本、通过/待复核/失败、总题数、平均/最慢耗时、成本、存储、Top 错误。
- **U7 只看异常**：我只看被标记的题（≤1%），每题带原因/证据（原卷页图、OCR 候选、修正记录），不需要逐页翻。
- **U8 金标准**：我能在一套独立标注的 30 本书上看到召回率/精确率/选项字符准确率/答案配对/图片召回/公式抽检；改一次代码就知道有没有回退。
- **U9 零静默**：任何丢弃/搬迁/改写都有 `ReviewNote`；没有记录的差额一律判红（延续现有 N4 口径）。
- **U10 成本/容量**：我知道每本书的耗时与 API/OCR 成本、每天/每月存储增量；能在 8 小时窗口内跑完目标批量。
- **U11 迁移**：新增一类输入（如手机截图）只加一个输入分类和对应目标，不改主流水线。
- **U12 每日无人值守**：定时任务每天自动扫描 `inbox/`、跑批、写日报、失败告警；我不需要守着。

## 5. 指标与验收（可量化）

### 5.1 指标定义（先在金标准上算，再谈目标）

| 指标 | 定义 | 分母/口径 |
|---|---|---|
| 题目召回率 | 金标准里的题，被系统切出且 `(page, number)` 匹配、正文/选项归一化重合 ≥95% 的比例 | 金标准题数（独立标注） |
| 题目精确率 | 系统切出的题中，能匹配到金标准题的比例 | 系统题数 |
| 边界准确率 | 匹配上的题中，起始/结束块与金标准完全一致的比例 | 匹配题数 |
| 题号完整率 | 金标准题号中，系统同页同号存在的比例；无解释的缺号/重号 = 0 | 金标准题号 |
| 选项完整率 | 金标准选项（键+文本）在系统选项中存在的比例 | 金标准选项数 |
| 选项字符错误率 | 匹配选项文本的归一化编辑距离 / 金标准字符数 | 匹配选项字符数 |
| 答案配对率 | 金标准「题—答案」对中，系统正确配对的比例 | 金标准答案对数 |
| 图片召回/归属 | 金标准图片被保留且挂到正确题的比例 | 金标准图片数 |
| 公式语义准确率 | 抽检公式渲染/语义与原卷一致的比例（人工） | 抽检公式数（每本 20–50 个） |
| 页面覆盖率 | 每页都有处理状态（成功/降级/失败），无静默跳过 | 总页数 |
| 静默失败率 | 丢弃/搬迁/改写但无 `ReviewNote` 的条数 / 总条数 | 审计记录 |
| 待复核率 | `needs_review` 题数 / 总题数 | 产物 |
| 自动通过率 | 0 个 blocking 错误且待复核率 ≤ 阶段阈值的书 / 总书数 | 批量台账 |
| 批量成功率 | 状态为 done 的书 / 投递书数（失败可重试，最终失败才计） | 台账 |
| 吞吐 | 单本中位/p95 耗时；每日完成书数（8h 窗口） | 台账 |
| 成本/存储 | 每本 API/OCR 成本；每页/每天/每月存储增量 | 账单/磁盘 |

**注意**：`needs_review` 只是代理指标，不等于准确率；下面的「当前 15.8%」不能直接说成 84.2% 准确。
真正的准确率必须来自金标准的独立标注。

### 5.4 验收方法

1. **金标准**：30 本，独立标注；10% 双标；题目边界 κ ≥0.9；标签版本化；分母只来自标签。
2. **单本评分器**：`npm run score -- <docId>` 输出 JSON + Markdown；每项指标有定义、分子/分母、样本数。
3. **批量验收**：`npm run batch -- <inbox>` 在 20 本（Phase 1）/100 本（Phase 2）上跑；记录耗时、失败、重试、去重、断点。
4. **无人值守**：Phase 2 连续 7 天定时跑；日报/告警；无人工逐本操作。
5. **生产抽样**：每月从新增书里抽 5–10 本人工核对，检查金标准是否漂移；不把抽样结果冒充全量。
6. **回归**：任何引擎/解析/OCR/修正变更，先跑 `check:accuracy`；指标下降即红；快速 `check` 继续 287 例。
