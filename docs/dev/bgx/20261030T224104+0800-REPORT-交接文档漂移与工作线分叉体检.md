### G01 [P1 / 已确认缺陷] 主入口的导航把「开发前沿」指向了非当前工作线

- 证据：
  - `docs/HANDOFF.md:8-11`「开发前沿在 **`feature/oxr` 分支**……要继续功能开发或读最新交接，先切到 `feature/oxr`」。
  - `grep -n "pick-classify\|挑题\|专题/类别" docs/HANDOFF.md` → **0 命中**：主入口全文没有提过当前工作线。
  - `git branch -vv`：`feat/pick-classify 5c6b32e`（无 upstream）、`feature/oxr 597e971 [origin/feature/oxr]`、`main 68d805c [origin/main: ahead 34]`。
  - `git rev-list --count main..feat/pick-classify` → **13**。
- 证据类型与结论：配置声明 + 运行验证；**已确认缺陷**（文档与实现不一致）。
- 触发与影响：任何接手者按 `AGENTS.md` 必读顺序读 HANDOFF，会被导向 `feature/oxr` 的 worktree；
  而当前 13 个提交的挑题归类 v2 工作在主仓库的 `feat/pick-classify` 上，主入口完全不可见。
  实际后果：在错误基线上开工（或以为功能尚未开始而重复实现），合回时制造大面积冲突。
- 优先级依据：不影响运行，但**直接决定下一个 Agent 是否走错分支**，且已在本次会话真实发生
  （需靠读计划文档末段才找回正确分支）。
- 建议：HANDOFF 顶部导航改为「三条工作线并存」的事实陈述 + 各自定位；§2 增「当前活跃工作线」小节，
  指向 `docs/plans/2026-10-30-pick-classify-workflow.md` 与 `feat/pick-classify`。
- 方案取舍：保留现状（零成本，但下一个 Agent 仍会走错）/ **局部修正导航**（改 10 行内文案，零业务风险）/ 结构调整（拆 HANDOFF 成「入口 + 三条线各自快照」，成本高、当前收益不足）。**推荐局部修正**。
- 依赖：无。规模：小。
- 验收：`grep -n "feat/pick-classify" docs/HANDOFF.md` 有命中；HANDOFF 中不再出现「先切到 feature/oxr」这类单向前沿指令。

### G02 [P1 / 已确认缺陷] 「`main` 已快进到功能分支」与事实相反

- 证据：`docs/HANDOFF.md:18-20` 写「`main` 已快进到功能分支，未 push」；
  `git merge-base --is-ancestor feature/oxr main` → **非 0（未并入）**；`git log --oneline -1 main` → `68d805c`。
  同段「两侧自 `076bcd0` 分叉时：main 侧 +4、功能侧 +9」与实测 `origin/main..main` = **34**、
  `origin/main..feature/oxr` = **111** 不符。
- 证据类型与结论：运行验证；**已确认缺陷**。
- 触发与影响：读者会以为「main 已含 OXR 全部成果」，据此在 main 上开工 → 丢掉 111 个提交的成果或产生反直觉冲突。
- 建议：改写为「`feature/oxr` **未**并入 `main`；`main` 落后 `origin/main` 34 个未推送提交」，
  并把计数改为「以 `git rev-list --count` 实跑为准」，不写死数字。
- 依赖：与 G01 同文件同段，合并为一次改动。规模：小。
- 验收：HANDOFF 中不再出现与 `git merge-base --is-ancestor` 结果矛盾的陈述。
