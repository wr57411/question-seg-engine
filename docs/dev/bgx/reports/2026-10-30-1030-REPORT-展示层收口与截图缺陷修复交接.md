## 2. 用户截图驱动的两次修复（这是本轮最需要交接的部分）

用户两次的反馈都是**一句话 + 一张截图**，且第一次反馈纠正了我自己的判断偏差，交接时要记住这个模式。

### 2.1 第一次：「这些绿色的字不要啊」

- **我最初的判断**：把绿字当成「配色不好看」，改成了黑字（§89）。
- **用户的纠正**：「我做这有什么区别？只不过是绿字变成黑字了。我只是在乎它颜色吗？」——
  **问题不在颜色，在那堆字本身就是多余的**。
- **教训**：用户描述症状（绿色），但不等于诉求（不要这些字）。**改颜色只是让它从「碍眼的绿」
  变成「不碍眼的多余」**。

### 2.2 真正的根因有两层（§90 + §91）

| 层 | 是什么 | 修法 |
|---|---|---|
| ① 表格被压平 | 原卷是 3 列 6 行知识清单表，上游拆成 10 行纯文本、单元格用 `\|` 隔开；每行按 bbox 单独算字号 ⇒ 字号参差、挤成一团 | `normalizeLayout` 按「x0/宽度一致 + 宽 > 页宽 60% + 行距 < 1.2 倍行高」分组，还原成 `kind:"table"` 交 `§76` 网格渲染 |
| ② OCR 补行错位 | 整页 OCR 没有位置信息，靠「锚点 + 宽度比例」硬配回洞；红标题条被 `classifyUncovered` 判成内容级洞 ⇒ 表格文字被画到页眉 | `renderPaper` 加 `ocrFill` 选项，**默认不画**，`?fill=1`/工具栏开关可开 |

**关键取证方法**（下次可直接复用）：
1. `python3` 打 `stages.json` 的 `pages[0].blocks`，逐块看 `bbox` + `text` —— 立刻看出「10 行 x0=73、宽 1848、y 等差 99」是表格行；
2. 再看 `pages[0].ocrFill` 的 `source` 字段 —— `page` 表示无位置信息，位置不可信；
3. **回原卷页图核对**（`pdftoppm -scale-to-x 1000`）确认「原卷这里到底有没有字」。

| 坑 | 现象 | 真相 | 记在哪 |

### 4.3 可以直接用的验证命令

```bash
npm run check                                   # 全门禁（typecheck + viewer 类型 + 测试 + 渲染审计 + bank）
npm run audit:ab --silent                       # 15 册切题指纹 A/B（改动前存一份基线）
# 浏览器视觉回归（截图空白先 dump-dom，别急着判渲染崩溃）
"/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" --headless=new --no-sandbox \
  --disable-gpu --disable-dev-shm-usage --hide-scrollbars --user-data-dir=$(mktemp -d) \
  --virtual-time-budget=12000 --window-size=1024,1250 \
  --screenshot=/tmp/x.png "http://localhost:4173/final/?doc=<docId>"
```

> `--user-data-dir` **每次换新的**：`restorePosition()` 会把滚动位置写进 localStorage，
> 复用 profile 会截到页面中段，看起来像「渲染空白」。

### 4.4 展示层三个可切换开关（同一套口径）

| 开关 | 默认 | 作用 |
|---|---|---|
| `?flow=1` / `?flow=0` | 自动（较短边 < 500） | 手机文本流 vs 纸面重建 |
| `?ocr=1` | 关 | OCR 补入行的青绿候选样式 |
| `?fill=1` | 关 | 把 OCR 补行画到纸面上（整页来源位置不可信） |

`final` 页工具栏对应三个勾选框：审计标记 / 显示 OCR 补行 / OCR 候选样式。
