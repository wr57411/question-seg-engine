## 0. 学习摘要（G1 产物）

### OXR 模型是什么

- SoMark 团队开源的**文档解析模型**，参数量仅 **1.3B**，国产（基于 GLM 架构）。
- **三榜第一**：OmniDocBench **97.18**、olmOCR-Bench **87.84**、DocParsingBench **87.76**
  （截至 2026-10 公开榜单），超过 Gemma-3-12B、Qwen3-VL-8B 等更大模型。
- 训练范式叫 **RSI（Recursive Self-Improvement，递归自提升）**：模型自己生成数据 →
  自我评估 → 迭代训练，官方称 10 轮内平均精度提升 12.3%。
- **两阶段架构**：独立的轻量布局分析模型（切版面区域）→ OXR 主模型（识别 + 阅读顺序）。
- 能力范围：文本、表格、公式（LaTeX）、化学结构式（SMILES）、图形/插图、阅读顺序；
  输入支持 PDF 与常见图片（png/jpg/jpeg/bmp/tiff/webp）。
- 微信文章演示过**数学试卷**逐题解析（题干/公式/图形还原），与本项目场景（试卷结构化）直接相关。

### 免费 API（免注册、免鉴权）

| 项 | 事实 |
|---|---|
| Base URL | `https://free-oxr.somark.cn/api/v1` |
| 鉴权 | `api_key` 字段**必须存在但不校验**，填 `dummy` 即可 |
| 端点 | `POST /parse/sync`（同步）；`POST /parse/async` + `/parse/async_check`（异步） |
| 限制 | 单文件 **≤10MB**、**≤20 页**；免费档排队处理 |
| 请求 | `multipart/form-data`：`api_key`、`file`、`formats[]`（json/markdown，无 zip）、`keep_header_footer`、`extra`（JSON 串：temperature/top_p/repetition_penalty） |
| 响应 | `{ code, message, warnings[], data }`；`data.result.outputs.json.pages[].blocks[]`，每块含 `idx/type/bbox/content/format/captions/img_url`，页含 `page_num/page_size{w,h}` |
| 错误码 | 1133 参数错误 / 1137 解析失败 |

### 与本项目的关系

本管线唯一上游耦合点是 `src/normalize.ts`（红线：换解析供应商只改这里）。
MinerU `layout.json` 与 OXR `json.pages[].blocks[]` 同构（页 → 块 → type/bbox/content），
OXR 有潜力成为：① **替代上游**（省 MinerU 额度）；② **第二解析源**（交叉核对，补 MinerU 漏识别）。

本项目已知的上游短板（HANDOFF §6，正是 OXR 可能补的）：
1. **整行漏识别**（第 1 题题号行曾整行丢失，靠 OCR 补回）；
2. **字母 O 系统性读成数字 0**（15 行，未修）;
3. **墨迹洞 45 处**（原卷有墨迹但解析+OCR 都没读出，含图注「甲/乙/丙」）。

## 2. 实验记录

### 2.1 G3 冒烟（题册 p1 PNG，2026-10-27）

- `POST https://free-oxr.somark.cn/api/v1/parse/sync`，`api_key=dummy`（免注册），
  单页 PNG 22.6s 返回，`code:0`、无 warnings。
- 响应：`data.result.outputs.{json, markdown}`；`json.pages[].blocks[]` 每块
  `idx / type / bbox / content / format / captions / img_url`，页含 `page_size{w,h}`。
- **坐标系**：PNG 输入时 page_size = 995×1369 = 图片像素；PDF 输入时 page_size = 1243×1712
  ≈ 150dpi 光栅（596pt × 2.085）⇒ **bbox 恒为光栅像素口径**，换算 pt 用 page_size 比例。
- 块类型（免费版）：PascalCase `Title / Text / Picture / Caption`；图片块 content 是
  指向 free-oxr 服务器的 markdown 图片 URL（会过期，正式接入需下载落盘）。
- 冒烟页即「MinerU 曾整行漏识别第 1 题题号行」的那页：OXR markdown 开头直接是
  `1. [广东广州 2022 月考] 如图, 建筑工人为检查墙砌得…` —— 整行完好。

### 2.4 G6 适配实验（OXR 做上游，现有引擎一行不改）

转换规则（`data/oxr/book-response.json` → `data/oxr/oxr-as-layout.json`）：
1. `pages[].blocks[]` → `pdf_info[].para_blocks[]`（⚠️ 引擎 `normalizeLayout` 读的是
   **para_blocks**，写 preproc_blocks 会静默得到 0 块 → 15 页全 1 栏 → 0 题，实测踩中）；
2. 类型映射 `Title→title / Text→text / Caption→text / Picture→image`（小写）；
3. bbox 按 `page_size` 比例从光栅像素缩放回 pt（题册 596/1243、821/1712）；
4. 文本块 `lines[{spans[{content}]}]`（块内 `\n` 保留，`matchFirstLine` 取首行仍有效）；
5. 图片块需**嵌套** `blocks[{lines[{spans[{image_path}]}]}]`（与真实 layout.json 的 image 块同构，
   直接 `lines` 顶层放会「图片归属 0」，实测踩中），`image_path` 从 markdown 语法剥出纯 URL。

同口径对照（同一 `scripts/oxr-eval.ts` 跑两个上游）：

| 指标 | MinerU 上游 | OXR 上游（转换后） |
|---|---|---|
| 切题数 | 83 | 83 |
| ok / 需校对 | 80 / 3 | **82 / 1** |
| review 性质 | 选项缺键（**疑似上游漏检**，热狗题等真实问题）×6 条 | 选项乱序 E↔A（**块粒度问题，非内容缺失**）×16 条 |
| 选项组 | 78 | 64（块更大，选项独立成块少） |
| 图片归属 | 97 | 90（OXR 检出 90 个 Picture 块） |
| 行内公式 | 102 | 319 |
| 分栏 | 15 页全 2 栏 | 6 页判 1 栏（块级几何粗于行级） |

结论：**管线对 OXR 上游可行**——83 题全切出、ok 率更高、review 全是可修的粒度问题；
主要缺口是**块级无行级几何**（影响分栏精度与字号保真的分母）与**多选题选项分块**。

### 2.5 局限（如实登记）

- 免费档 10MB / 20 页限制：23 页的答案册必须走正式版；正式版与免费版 schema 不同。
- bbox 为光栅像素（≈150dpi），缩放回 pt 有约 1px 级标定误差；无行级 bbox、无字号信息
  （字号保真度审计在 OXR 上游下没有分母，需另行标定）。
- 图片托管 URL 会过期（官方有 image-persistence 指南），正式接入必须下载落盘。
- 公式「正文误包 `$...$`」噪声需 `formula.ts` 检测（检测不改写，交人工决策）。
- 块粒度粗 → 分栏 6 页判 1 栏、选项组少 14 个 —— 版面层可能需要为 OXR 上游调阈值
  （触发「单卷过拟合」风险 §6-8 的同类问题，扩数据面前先不动）。

## 3. 结论：OXR 能否更好完成这个项目

**能，且在三个既有痛点上是直接解药；但作为唯一上游替换 MinerU 还不是首选，第一落点是「第二解析源/交叉核对」。**

> **2026-10-27 深夜补充（据 §4 实测修正措辞）**：上面这个「能」在**切题指标**上成立，
> 但把产物真正喂给成品页时，先是满屏破图 + 正文 3px（不可读）。修掉 3 个适配缺陷后才可读。
> ⇒ 准确表述应为：**「管线兼容」已证；「页面上可用」刚达标但仅两屏抽样**，
> 而**「替代 MinerU」还差**答案册 schema 归一（G10）与指标独立分母（G13）。
> 单看 83/83 就下"能替代"的结论，是拿后台数字当验收证据——本项目红线不允许。

> **2026-10-28 定稿（G9–G13 完成后）**，结论收敛为三条：
>
> 1. **能力定位**：OXR 适合做**第二解析源 / 交叉核对**，不适合作唯一上游。
>    内容识别确实更强（题号零缺号、`O点` 零错、图注直读，且 16/16 图注候选回原卷核对为真），
>    但只有**块级**几何 ⇒ 成品页排版精度不及 MinerU（压图 7 页 / 右栏溢出 3 页）。
> 2. **已可日常使用**：`npm run daily -- <pdf> --parser oxr` 一条命令，超 20 页/10MB 自动分片，
>    `src/` 零改动；实测两卷切题数（67/9、84/13）与 MinerU **完全一致**。
> 3. **落地价值已量化**：**29 条修复候选**（13 条 O→0 + 16 条图注），
>    其中 16 条图注 + 1 条 O→0 已回原卷核对为真，可直接作为改写依据的输入。
>
> 未闭合：字号保真度缺**独立分母**（§4.10）、排版精度受限于上游无行级几何（§4.5）、
> 候选尚未落地改写（须单独决策，红线）。

1. **MinerU 的整行漏识别**（本项目两条 OCR 补行链路的存在理由）：OXR 在题册上
   83 个题号形态一次读全、零缺号 —— 该痛点在 OXR 上游下基本消失。
2. **字母 O 系统性读成 0**（HANDOFF §6-13，挂了未修）：OXR 16/16 全部读对、零错。
   该问题的「改写数据须显式决策」现在有了第二来源可对照，修法成本大幅下降。
3. **图注丢失**（HANDOFF §6-14，MinerU+OCR 双漏的洞）：OXR 有专门的 Caption 类型，
   甲/乙/曲辕犁/直辕犁全部读出。
4. 管线兼容性已实证：转换规则 5 条 + 现有引擎 0 改动 = 83/83 切题、ok 率高于 MinerU。
5. **建议的下一步（未实施，待拍板）**：

判据都是**页面截图**，不是数字——这三个缺陷在「切题 83/83」这个指标下完全隐身。

| # | 症状（截图可见） | 根因 | 修法 |
|---|---|---|---|
| A | 90 张图**全部**显示成「图片块」破图 | 快照契约要求 `images[].path` 是**裸文件名**（展示层无条件拼 `/data/out/<doc>/images/`），而 OXR 给的是 `https://free-oxr...` **绝对 URL** ⇒ 拼成 `images/https%3A%2F%2F...` 必 404 | 下载落盘 + 改写为内容哈希文件名（§2.5 早已预告"正式接入必须下载落盘"，一直没做） |

| C | 修完 B 后文字**横向冲出栏宽、压到邻栏**（渲染字号被放大 ~45%） | 我给 line 的 bbox 高度是**行距**（1.45×字号），但展示层拿 bbox 高度当**字号**用 ⇒ 字号被放大 1.45 倍 | bbox 改成**墨迹口径**：高度 = 字号本身，垂直居中于行距内（与 HANDOFF §5-9「CJK 墨迹高 ≈ 1em」同源） |

> **方法教训（值得进 lessons）**：A/B/C 三个缺陷没有一个是"引擎错了"或"展示层错了"——
> 全是**适配层与契约不匹配**。而它们全部在「切题 83/83、ok 82」这个数字下不可见。

### 4.2 适配器怎么折算（`scripts/oxr-adapter.ts`）

- **坐标系**：OXR bbox 是 150dpi 光栅像素（题册 `page_size = 1243×1712`）；
  以纸宽为锚缩放到 pt（`596 / w`），页高按同比例换算 ⇒ 与 MinerU `page_size` 同口径。
- **字号联立解**（缺陷 B 的解法）：
  ① 文本填满块宽 ⇒ 每行 em 数 = 块宽 / 字号；
  ② 行高 = 1.45 × 字号；
  两式联立 ⇒ `字号² = 块高 × 块宽 / (1.45 × em总数)`。
  ⚠️ 关键坑：**OXR 正文块多数不带 `\n`**（整段文本 + 块级 bbox），
  第一版按 `\n` 数行数得到 `p50 = 26.2pt`（正文算出 26pt，明显荒谬）——
  改成联立解后 `p50 = 10.6pt`，与纸面实际字号吻合。
- **折行**：按 em 宽度（CJK 1.0 / ASCII 0.55 / 空格 0.3）折成物理行，
  用实折行数回代校正字号一次（一轮收敛）。
  这是**估算**，必然有误差 ⇒ 4.4 的叠字/溢出来源于此，不是数据错误。
- **图片块结构**：必须嵌套 `blocks → lines → spans → image_path`
  （直接放 `lines` 顶层会「图片归属 0」，§2.4 已记）。
- **行级几何的附带收益**：分栏检测从"块级"变成"行级"，原先 15 页有 6 页被误判成**单栏**。

### 4.8 接入 daily：`--parser oxr` 一条命令（2026-10-28，G12）

**目标**：让 OXR 从「评估脚本的手工三步」变成「和 MinerU 一样的一条命令」。

```bash

npm run daily -- <卷.pdf> --parser oxr --no-ocr   # 跳过 OCR 补行（更快）
```

**架构（关键：引擎零改动）**：

```
<卷.pdf> ──oxr-client.ts──▶ OXR 免费 API（超 20 页/10MB 自动分片）
              │
              ▼ OxrResponse
         oxr-convert.ts ──▶ MinerU 同构 layout.json + images/
              │                    （这一步就是「换解析供应商只改归一化层」）
              ▼
        既有下游 ②导出快照 ③OCR补行 ④体检摘要 —— 原样复用，一行没改
```

- `scripts/oxr-convert.ts`：纯转换模块（无 argv、无打印），daily 与 CLI 共用，
  避免「CLI 一份、daily 一份」两处漂移。
- `scripts/oxr-adapter.ts`：薄 CLI 壳（约 40 行），只读参数/落盘/打印。
- `scripts/oxr-client.ts`：API 客户端 + **自动分片**。
- `src/` **零改动** —— 这是本设计最重要的一点：红线「换/加解析供应商只改归一化层」得以兑现。

**分片策略**（免费档 ≤20 页 且 ≤10MB，实测原卷普遍超标）：

1. 先按 20 页切一片，用 `pdfunite` 合成临时 PDF 并**实测体积**；
2. 若超 10MB，页数减半重试（下限 1 页）；
3. 单片仍超限则明确报错（该页可能是高分辨率扫描，需降采样）——**不静默降质**；
4. 逐片上传，`page_num` 重写为全局页序后合并。

### 4.10 指标：字号保真度在 OXR 上游下算不算数（2026-10-28，G13）

**实测**（`node scripts/audit-render.mjs <docId>`）：

| 卷 | 扫描文本块 | 可判块 | 中位 ratio | 判定 |
|---|---:|---:|---:|---|
| MinerU 题册（基线） | 1310 | **198** | 1.0211 | ✅ 通过（∈[0.93,1.07]） |
| OXR 题册 | 2018 | **151** | **1.0040** | ✅ 通过 |

单看这张表，结论会是「OXR 上游下字号保真度**更好**」。**但这个结论不成立**，原因是循环论证：

- 判据的 `ratio` = **渲染宽度 / bbox 宽度**；
- 而我给 OXR 块的 `font_size` 是**从 bbox 反推出来的**（`字号² = 块高×块宽/(1.45×em)`）；
- ⇒ 「用 bbox 推字号，再用字号去比 bbox」**必然接近 1**，这是自我一致，不是与原卷一致。

MinerU 版没这个问题：它的 `font_size`/行 bbox 是**上游实测**的，不是从 bbox 反推的，
所以那条 ratio 才是真判据。

⇒ **G13 结论**：字号保真度这一项，在 OXR 上游下**当前没有可信的自动门**。
现在的 1.0040 **不能作为验收证据**（与红线「判据分母必须来自被检验对象之外的独立来源」
相冲突 —— 这里的"独立来源"应是**原卷页图上的墨迹行高**，而 bbox 不是）。

**可行的独立判据（未实现，留给后续）**：
从原卷页图量墨迹行高（项目已有 `renderGrayPages` 灰度图 + 水平投影能力，
`unfilledContentHoles` 已在用），把「原卷墨迹行高」与「渲染字号」对比。
这样分母才真正独立于 OXR 的 bbox。

**当前替代验收**（已在做）：15 页全量人工截图审板（§4.5）+ 逐条候选回原卷（§4.9）。
诚实的表述是：**OXR 上游的页面对不对，目前靠人眼，不靠数字门。**

**顺带确认的好消息**：`audit:render` 的另外 9 项判定（上标/下标标点、残留反斜杠、
残留花括号、裸上下标、选项粘连、未覆盖 LaTeX 命令、命令切分歧义）在 OXR 卷上**全部为 0**
—— 这些判据不依赖 bbox 口径，是**可信的**。说明 §4.4 的 E/F 修复确实干净。

#### 4.10.1 更正 + 独立判据的尝试（同日，C 项）

**上面那段的有个前提是错的**：我写「MinerU 版的 `font_size` 是上游实测的」。
实测发现 —— **MinerU 卷的 `maxFontSize` 也全是 0**（`normalizeLayout` 后 964 个 text 块，
`maxFontSize>0` 的数量为 **0**）。也就是说：

> **两份数据都没有上游字号真值**，展示层的字号**都是从 bbox 高推的**
> （`fontFromLineHeight(h) = h × 1.03`）。所以 `audit:render` 的字号项
> **在 MinerU 卷上同样是自洽性检查，不是保真度检查**。

这不只是 OXR 的问题，是**整个项目**在这项上的缺口（只是 MinerU 卷页面看起来对，
所以一直没被发现）。

**尝试建立独立分母**：`scripts/audit-oxr-font.ts` ——
用 `pdftoppm -gray` 渲染原卷（与墨迹覆盖率同一套机制），对每个文本块的 bbox 区域做
**水平投影**找墨迹行，用「行高(px) → pt → ÷1.45」反推实测字号，与展示层字号对比。

**结果：判据未标定，暂不可用**（如实登记）：

| 卷 | 可判块 | ratio p10/p50/p90 | 判定 |
|---|---:|---|---|
| MinerU 题册 | 686 | 1.556 / **1.711** / 1.926 | ❌ 中位偏离 71% |
| OXR 题册 | 516 | 1.908 / **2.372** / 3.618 | ❌ 中位偏离 137% |

**MinerU 卷本该是最可靠的对照组**（页面看着是对的），它却给出 1.711 ⇒
问题不在被测数据，在**测量方法**：水平投影按「连续暗像素行」切行，
而 CJK 字形在垂直方向中间常有空隙（如「二」的中间），会把一行切成多段、**系统性低估行高**。

⇒ 结论：
1. 脚本作为**起点**保留（分母来自原卷像素，方向正确）；
2. **标定之前不得用于验收**（当前数值不可引用）；
3. 正确的标定方式：拿**已知字号的对象**（如版面标题，可用字高/字数交叉核对）去校准投影参数，
   而不是拿它去判被测数据。

**所以 G13 的最终答案**：字号保真度目前**在两份数据上都没有可信自动门**，
只能靠人工截图审板（§4.5 已对 15 页做全量）。这是本轮如实登记的缺口，不是已解决项。

#### 4.10.2 尺子标定完成：OXR 的字号与原卷一致（同日，C 项收尾）

上一小节的两处**测量错误**已定位并修正：

1. **不该除以 1.45**：墨迹跨度**本身 ≈ 字号（1em）**，1.45 是「行距 / 字号」，
   只在把行距换算成字号时才用。第一版多除了一次，系统性低估 31%。
2. **不该按「连续暗行段」切行**：CJK 字形垂直方向中间常有空隙（「二」的上下两横之间），
   一行会被切成多段。改为量**整块墨迹垂直跨度**（第一暗行 → 最后暗行）。

另加一条约束：**只取单行块**（跨度 / bbox 高 ≥ 0.85）—— 墨迹跨度 ≈ 字号只对单行成立，
多行块的跨度是多行总高，拿它当字号会严重高估。

**标定后结果（2026-10-28）**：

| 卷 | 可判块 | ratio p10/p50/p90 | ∈[0.80,1.25] 占比 | 判定 |
|---|---:|---|---:|---|
| MinerU 题册（对照组） | 412 | 1.073 / **1.129** / 1.180 | 99.5% | ✅ |
| OXR 题册 | 44 | 1.017 / **1.067** / 1.187 | 100% | ✅ |

**结论（这条是本轮对 OXR 最重要的正面证据之一）**：

- 对照组 MinerU 的 p50 = 1.129 ⇒ **尺子本身可用**（已知页面正确的卷子被量出 ≈1）。
- OXR 的 p50 = 1.067，**与对照组同量级、甚至更接近 1** ⇒
  我们从 bbox 反推的字号**与原卷墨迹一致**，而不仅是与 bbox 自洽。
  这比 §4.10 那句"绿了也不能当证据"要强：现在是**有独立分母的绿**。

**系统性偏置 7–13%（非 0）**：`bbox高 × 1.03` 比实测墨迹略大，合理 ——
bbox 通常含一点上下留白，墨迹不一定顶满 em 框。落在 ±15% 容忍内。

**局限（如实登记）**：
- OXR 侧**可判块只有 44**（MinerU 412）：因为 OXR 被拆成行级块，块 bbox 很小，
  多数不满足「单行块 + 区域够大」的门槛。样本量偏少，代表性弱于对照组。
- 只覆盖题册，答案册未跑（字号更小，可能在 150dpi 下更接近像素量化误差）。
