# PaddleOCR-VL 能否补「解析遗漏」—— 可行性实测（2026-10-10）

> 📍 交接导航：本文件是**测量证据（历史数据，非当前状态）**——被 `DECISIONS.md` 引用为口径依据。
> 当前状态、未闭合风险与红线见 **[docs/HANDOFF.md](../HANDOFF.md)**；通用约定见 **[AGENTS.md](../../AGENTS.md)**。


**结论：能。** 且与引擎已有文本**逐字一致**（对照组），可作为「候选补全」使用；
但**不能当作可信输入直接合入**（有 OCR 错字），且必须按**整行/整段**裁图、避开插图。

## 方法

`data/out/ocr-fill.py`：读快照 `pages[].uncovered`（内容级）→ 按 bbox 从 `origin.pdf`
以 300dpi 裁图（外扩 8pt）→ base64 喂给 MCP 的 `paddleocr_vl`（`output_mode=simple`,
`return_images=false`）→ 收集文本。一个 MCP 会话处理全部区域。

## 四个必须处理的坑（都有实测）

1. **裁图不能覆盖插图**。实测把 A 选项行裁到 x=292（插图 bbox 是 [194,201,282,283]）后，
   输出里混进了 `<div style="text-align:center;"><img src="imgs/…" /></div>` 图片占位符。
   裁到 x=192（避开插图）后输出干净。⇒ 裁图框必须**减去该页图片块的 bbox**。
2. **未覆盖区域只是「行的碎片」**。例如 A 选项被拆成 [54,204,183,215]（第 1 行）
   与 [67,229,144,239]（第 2 行）两块。要还原可读文本，得按**整行**裁，而不是按碎片裁。
3. **输出有 markdown / HTML 噪声**：出现过 `###`、`##`、`：777`、
   `<div …><img …/></div>`。合入前必须清洗。
4. **OCR 会错**（实测 `D 当口将` ← 原卷是 `D. 当只将`，而引擎这行是对的）。
   ⇒ OCR 只能用于「引擎为空」的地方，且结果必须标为**候选**，不能静默替换。

## 代价

- **延迟极不稳定**：3.5s ~ 86.7s / 区域（同一批里差 25 倍）。31 个区域估算 **15–45 分钟**。
  ⇒ **不能进 `npm run check`**（那是个秒级门），必须做成**显式触发的构建步骤**。
- **非确定性**：远端模型，同样输入不保证同样输出 ⇒ 不能做判定项，只能做「候选填充」并记录来源。
