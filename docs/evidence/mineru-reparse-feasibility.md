# MinerU 重跑能不能补漏？——「抽卡」方案的实测裁定（2026-10-10）

> 📍 交接导航：本文件是**测量证据（历史数据，非当前状态）**——被 `DECISIONS.md` 引用为口径依据。
> 当前状态、未闭合风险与红线见 **[docs/HANDOFF.md](../HANDOFF.md)**；通用约定见 **[AGENTS.md](../../AGENTS.md)**。


**结论：`抽卡`（同输入重跑）无效；但它的一个变体——`多切法合并`——有效且可自动验证。**

## 一、抽卡无效（两条独立证据）

### 证据 1：同一输入重跑，输出**逐字节相同**

把热狗题区域裁图（`hotdog-p5-05.png`，379821 bytes）连续上传两次：

```
第 1 次：batchId=e0027bd6-…  耗时 5s  markdown 189 字
第 2 次：batchId=7df1536a-…  耗时 9s  markdown 189 字
确定性判定：两次 markdown 完全相同 ⇒ 该输入下**确定**（抽卡无意义）
```

batchId 不同、耗时不同（说明**不是缓存命中**），但**内容一字不差** ⇒ MinerU 在这条链路上是确定的。

### 证据 2：换分辨率（同内容、不同像素）结果也几乎相同

同一区域 @300dpi 与 @450dpi 分别解析，输出**几乎逐字相同**，连错字都一样
（两版都写 `对熟"执狗"的合力`，原卷是 `热狗`）：

```
@300dpi: …下列说法正确的是 ( )A.生"热狗"对单根金属圆热狗柱的压力大小为 5/8 G B.…C. 两根金属圆柱对生"热狗"的合力大于对熟"执狗"的合力
@450dpi: …下列说法正确的是 ( )A.生"热狗"对单根金属圆柱的压力大小为 5/8 G B.…C.两根金属圆柱对生"热狗"的合力大于对熟"执狗"的合力
```

⇒ **分辨率不是有效的扰动维度**。

### 附带：没有可调的采样参数

客户端 `createUpload()` 只发 `{ name, fileSize }`（见 `src/mineru/client.ts:64-70`），
**没有 model / temperature / is_ocr 之类的旋钮**。即使想「调高温度多采样」，接口也不给。

## 二、换切法（喂区域裁图）确实改变结果，但**不是单调变好**

| 案例 | 输入 | 结果 |
|---|---|---|
| **热狗题** | 整页 PDF（原解析） | 题干读完就断，**A/B 选项全丢** |
| | 热狗题区域裁图 @300dpi | **补回了**：`A.生"热狗"对单根金属圆柱的压力大小为 5/8 G` `B.…5/6 G` ✓ |
| **滑轮题** | 整页 PDF（原解析） | 至少有 C/D 首行 |
| | 滑轮题区域裁图 @300dpi | 只读到题干，**A/B/C/D 四个选项整段丢失** ✗ |

裁图本身经人工核对是**正确的**（含完整 A/B/C/D 与那行「动时，A 的轴所受压力变大」），
所以这是模型的漏读，不是我裁歪了。

⇒ **换切法是把错误换个地方，不是「抽到正确的那张」。**

## 三、可用的变体：**多切法合并 + 用墨迹覆盖率当裁判**

既然不同切法**丢的东西不同**（整页丢 A/B、裁图丢 C/D），那么：

1. 对同一页跑**多种切法**：整页 / 按题裁 / 按栏裁 / 按行裁
2. **取并集**：每个「解析遗漏」区域，从任一覆盖它的结果里取文本
3. **裁判**：合并后重跑**墨迹覆盖率检查**（Task 16 已有），**未覆盖内容级区域必须变小**，
   否则这次合并不算数 —— 这是**可自动化的判据**，不需要人工判断「哪张卡对」
4. 结果标为**候选**（来源可溯），不静默替换（G1）

> 为什么这比「抽卡」靠谱：抽卡缺一个**自动判据**（凭什么说这次抽对了？）；
> 而「未覆盖墨迹缩小」是机器能算的，正好补上这个缺口。

## 四、与 PaddleOCR-VL 区域 OCR 的对比

| | MinerU 裁图重解析 | PaddleOCR-VL 区域 OCR |
|---|---|---|
| 单次耗时 | **5–9s**（稳定） | 3.5–86.7s（差 25 倍） |
| 输出形态 | **结构化**（content_list / layout，可直接进管线） | 纯文本 |
| 失效模式 | 会**整段丢**（滑轮题选项全丢）；阅读顺序会乱（`← 2.4R →` 混进正文） | 行精确裁图时干净；但**会错字** |
| 判据 | 同为墨迹覆盖率 | 同 |

⇒ **两者互补**：先用 MinerU 多切法合并（快、结构化），剩余用 OCR 兜（行级、稳）。

## 五、阻塞项：整份 PDF 重跑受网络环境阻塞

试跑整份 PDF 重解析：**API 提交成功、解析完成（`state: done`）**，
但结果 zip 从 `cdn-mineru.openxlab.org.cn` **间歇性下载失败**：

- 几分钟前同一 CDN 能下（热狗/滑轮裁图的 zip 都下成功了）
- 之后 `curl` 直连 **exit 35（SSL connect error）**，`fetch` 3/3 失败
- DNS 正常（真实 IP，非 fake-IP），但环境里有 `HTTP_PROXY/HTTPS_PROXY`

⇒ 「整页重跑」这条路**当前被代理/网络挡住**，要先解决才能做文档级对照实验。

# 补充（2026-10-10 16:10，用户关掉 Clash 后复测）

## 一、原来的「间歇性 CDN 下载失败」——**不在了**

整份 PDF 的结果 zip 从 `cdn-mineru.openxlab.org.cn` **一次下载成功**：

```
下载: HTTP 200 size=9528761 time=1.044552s   （9.5MB，zip 106 个条目，含 layout.json）
```

## 二、但关掉 Clash 暴露了一个**更根本**的问题：`mineru.net` 证书主机名不匹配

```
*  subject: CN=*.mineru.org.cn
*  subjectAltName does not match host name mineru.net
* SSL: no alternative certificate subject name matches target host name 'mineru.net'
→ curl exit 60 / node fetch TypeError: fetch failed
```

- **不是沙箱或链路问题**：对照 `pypi.org` 看到的是它自己的真证书
  （`CN=pypi.org`, GlobalSign）；`openssl s_client` 对 mineru.net 也报
  **`Verify return code: 0 (ok)`**（openssl 默认不校验主机名），issuer 是 DigiCert RapidSSL。
  ⇒ **是 `mineru.net` 自己发了一张名字对不上的证书**。
- **之前能用，是 Clash 带 TLS 处理把它盖住了**。关掉即暴露。
- **影响面不止本次实验**：项目的 `MineruClient` 走 node `fetch`，所以
  **`npm run real-pipeline` 现在会直接失败**。
- **试过换入口，走不通**：`https://mineru.org.cn` 证书匹配（HTTP 200），
  但它的 API 返回 **`401 C1114 API token scope forbidden for this domain`**
  —— token 只授权给 `mineru.net`，换不过去。
- 可用选项：① 重新打开 Clash（它一直在掩盖这个问题）；
  ② 给该 host 放宽 TLS（`MineruClient` 构造函数**支持注入 `transport`**，可只对这一处放开，
  但属于安全权衡，应做成显式 opt-in）；③ 找 MinerU 官方确认证书是否已修。

## 三、顺带拿到**决定性**结论：文档级重跑也是逐字节相同

CDN 通了之后，把整份 PDF 的重解析结果与现有 `layout.json` 逐项对照：

# 补充 2（2026-10-10 16:50，全量 31 区域重解析实验）

## 先修掉一个环境问题：沙箱进程**不走 Clash 的 TUN**

```
CDN ① 默认(沙箱代理 60644) → exit 35 ✗
CDN ② --noproxy '*'(TUN)   → exit 35 ✗
CDN ③ -x 7897(Clash 代理)  → 403    ✓   ← 唯一能通的路径
```

⇒ 沙箱里跑的一切（含 `npm run real-pipeline`）都必须**显式走 Clash 的 HTTP 代理口**。
node 内置 fetch 不认 `HTTP(S)_PROXY`，给外部 `undici` 的 ProxyAgent 会 `UND_ERR_INVALID_ARG`；
可行写法是 `import { fetch, ProxyAgent } from "undici"` + `dispatcher`（实测 HTTP 200）。
`MineruClient` 支持注入 `transport`，本实验已用它接上 7897。

## 两种 framing 的全量结果

| framing | 可处理 | 「覆盖」 | 问题 |
|---|---|---|---|
| **细横条**（区域所在栏 × 上下 ±12pt） | 31/31 | 10（32%） | **文本大量邻行碎片噪声**（`.手际刀小凹吗D.摩擦力大于…八上`） |
| **整题**（最近一题的并集 bbox） | 17/31（14 跳过） | 9（53%） | 文本仍是残的；**覆盖判据不可信** |

## 结论：**这条路的度量与文本质量都还没过关，数字不可信**

三个必须解决的问题（都有实测证据）：

1. **覆盖判据太弱**：我用「恢复块的 bbox 与区域相交」判定补上。p5 热狗题因此被判「补上」，
   但恢复的其实是**题干**（`1.[山东泰安2022一模]路边面简化示意图…`，还缺字），
   不是缺的 A/B 选项 —— **bbox 相交 ≠ 文本正确**。判据必须升级为「恢复文本覆盖该区域的墨迹」。
2. **「找题」判据对跨栏题失效**：我按「同栏 + 垂直最近」找题，p14/p7 的跨栏题被判成异栏 → 14 个区域直接跳过。
3. **framing 选择是核心难点**：细条 → 噪声；整题 → 文本残缺且可能整段丢（早前滑轮题实测选项全丢）。

## 与 OCR 路线的对比（同一批区域）

| | MinerU 区域重解析 | PaddleOCR-VL 区域 OCR |
|---|---|---|
| 文本质量 | 差（噪声/残缺） | **干净**（`A. 生"热狗"对单根金属圆柱的压力大小为 5/8 G`） |
| 可否逐字核对 | 难 | **可以**（与 300dpi 原卷裁图逐字比） |
| 结构化 | 有 bbox（但 framing 变了，映射回页坐标有误差） | 纯文本 |
| 耗时 | 5–15s/区域 | 3.5–86.7s/区域 |

⇒ **当前证据支持走 OCR 路线**：它的输出是干净、可逐字核对的文本；
MinerU 重解析的成本高、噪声大，且「多切法合并」还需要先解决上面三个问题。
